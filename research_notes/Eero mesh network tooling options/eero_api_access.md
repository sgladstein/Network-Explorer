# Programmatic access options for eero mesh Wi-Fi (state as of Nov 2026)

Method note: support.eero.com and eero.com could not be fetched from this research session (DNS blocked by the sandbox), so official eero claims below come from search-engine summaries of those pages, not full-page reads. GitHub repos were cloned and their code and docs read directly. On 2026-11-05: fulviofreitas/eero-api was at v8.4.1 (last commit 2026-11-04), schmittx/home-assistant-eero's last commit was 2025-09-19, and 343max/eero-client's last commit was 2024-02-08.

## 1. Official APIs: does eero offer any, what do they cover, and who can use them?

### Takeaway
Home users get **no official public API for controlling or monitoring their network**. There are three official routes, all of them closed or narrow:
- **Data Portability API**: read-only, OAuth 2.0, EU-focused, and only for vetted third parties under NDA.
- **eero Insight web portal**: for eero Business owners and ISPs, with ISP-only "Insight Exchange" APIs.
- **Data Management download** at account.eero.com: a one-off copy of your own device data.

Everything a hobbyist builds in practice runs on the reverse-engineered mobile-app cloud API.

### Cited Findings
**Data Portability API (third parties only)**
- eero runs a "Data Portability" program for third parties. To join, a third party completes a Third Party Security Assessment, emails privacy@eero.com and signs an NDA. "Once the NDA is executed, eero will share the full documentation with you via email." eero adds that its APIs "can be called directly, as we do not provide extra libraries." — [eero Data Portability Third-Party Onboarding](https://support.eero.com/hc/en-us/articles/40180105962139-eero-Data-Portability-Third-Party-Onboarding)
- Search summaries of the same program describe the API as OAuth 2.0 and read-only, for approved third parties. "A full API specification will be provided once you have completed the Third party Security Assessment and are onboarded." — [eero.com mirror of the onboarding article](https://eero.com/support/articles/how-do-i-onboard-with-eero-data-portability-as-a-third-party)
- The program is framed around EU customers. "Customers with a network in the European Union have distinct data portability rights, which allow you to share and store your eero data with third parties."
  - Sharing goes through third-party apps that integrate with eero's API and send the user to an eero login page to authorize access.
  - The user picks either a one-time transfer or continuous access for a set period.
  - Access can be revoked in Data Management at account.eero.com. Data already shared cannot be recalled.
  - Users can also download a copy of their device data from Data Management. Portability requests go to privacy@eero.com.
  - Sources: [eero Data Portability](https://support.eero.com/hc/en-us/articles/40180112699931-eero-Data-Portability); [How do I share my eero data with third parties?](https://eero.com/support/articles/how-do-i-share-my-eero-data-with-third-parties)
- The EU Data Act (Regulation (EU) 2023/2854) has applied since 12 Sept 2025. It gives users rights to access and port data generated by connected devices. — [ayedo Data Act overview](https://ayedo.de/en/data-act/). The eero pages seen did not cite the Data Act by name; see Inferences.

**eero Insight for eero Business**
- Only Business Network Owners with an eero Business subscription can use eero Insight. Network admins cannot.
- It is reached at insight.eero.com or from the app's Settings.
- It covers network status, connected devices, speed tests and bandwidth monitoring, multiple Wi-Fi networks (up to four), and a Visitor Engagement dashboard that requires the captive portal.
- No public API is documented for it.
- Source: [eero Insight for eero Business](https://support.eero.com/hc/en-us/articles/19653076310555-eero-Insight-for-Business)

**eero for ISPs (Insight and Insight Exchange)**
- "Insight Exchange allows you to export data and set up integration with other systems via APIs." — [eero for ISPs](https://eero.com/isp)
- A 2021 eero press release described "Advanced APIs and insight exchange to integrate eero Insight into existing ISP software through APIs to enhance network management for reboots, topology, outage information and more." This is older but still the clearest public description. — [BusinessWire 2021-10-25](https://www.businesswire.com/news/home/20211025005257/en)
- eero Insight later gained AI-powered capabilities. Existing ISP partners are told to contact their eero Partner Success Manager to get them, so access is partner-only. — [eero blog: AI-powered capabilities now available in eero Insight](https://eero.com/blog/articles/ai-powered-capabilities-now-available-in-eero-insight)
- eero for Service Providers launched in 2020 as the ISP program. — [Help Net Security 2020](https://www.helpnetsecurity.com/2020/10/08/eero-for-service-providers/)

### Inferences
- A home user cannot get credentials for Insight Exchange: it is ISP-only.
- eero Business Insight is a web UI only and needs a Business subscription, so it is not an API.
- The Data Portability API is designed for third-party services, not for self-access. A determined EU user might technically onboard as their own "third party", but the security assessment and NDA make this impractical. The Data Management download is a one-off export, not a live feed.
- The program's timing (article IDs from 2025) and its EU-only scope strongly suggest it is eero's EU Data Act compliance mechanism. This is an inference; eero's pages did not say so.

### Gaps
- The Data Portability API's data categories, endpoints and token lifetimes could not be read. The spec is NDA-only, and the support pages could not be fetched in full.
- It is unknown whether the Data Management download includes Wi-Fi telemetry (signal, node) or only device and usage records.
- No source confirmed whether eero PRO (the professional-installer program) has any API.
- No official public developer portal was found as of 2026.

## 2. Unofficial APIs and clients: what exists, is it maintained, and how does auth work?

### Takeaway
All unofficial tools talk to the same undocumented mobile-app cloud API at `https://api-user.e2ro.com/2.2` (some resources live on `/2.3`).
- **Auth** is passwordless: you POST an email or phone number and receive a one-time code by email or SMS. The verified `user_token` is sent as an `X-User-Token` header and/or a `s=<token>` cookie.
- **Session lifetime** is controlled by the server. Clients see a 401 `error.session.refresh` when the session needs a refresh, and refresh via `/2.2/login/refresh`.
- **Most actively maintained (late 2026):** fulviofreitas/eero-api (Python, v8.4.1, Oct 2026) and its ecosystem.
- **Older and stale:** 343max/eero-client (2024). schmittx/home-assistant-eero (Sept 2025) has been overtaken by HA forks.
- **Amazon login:** "Sign in with Amazon" accounts don't work with any of these tools. The workaround is a separate email or phone eero account invited as a network admin.

### Cited Findings
**API host and auth flow**
- The API host constant is `API_HOST = "https://api-user.e2ro.com"` and the default endpoint is `.../2.2`. Separate constants exist for login, login/verify, login/refresh, logout and account. — [eero-api src/eero/const.py](https://github.com/fulviofreitas/eero-api/blob/HEAD/src/eero/const.py)
- The login flow, per the eero-api docs:
  1. POST a form-encoded body with `login=<email or phone>` to `/2.2/login`. The response contains a `user_token`.
  2. POST `code=<code>` to `/2.2/login/verify`, authenticated with that token. The token itself becomes the verified session; verify does not issue a new token.
  3. If needed, `/2.2/login/resend` re-sends the code (added in v8.4.0).
  - Source: [eero-api wiki: Authentication](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Authentication.md)
- How the token travels:
  - `X-User-Token: <token>` header is the primary credential.
  - `Cookie: s=<token>` is the legacy form, sent by default.
  - There is no refresh token. The only signal is the server's 401 `error.session.refresh`, after which the client POSTs to `/2.2/login/refresh` and replays the request.
  - Errors like `error.session.expired`, `.invalid` or `.revoked` mean you must log in again.
  - "There is no client-side session expiry."
  - Source: [eero-api wiki: Authentication](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Authentication.md)
- 343max/eero-client also uses `api-user.e2ro.com/2.2/{}` and sends the cookie `s=user_token`. Its author says the API was found "by intercepting the traffic of the eero app." It supports login and verify (phone number plus SMS code), user_token refresh, account, network, device list and reboot. It "only works for email/phone number login, not for users who login with their Amazon account." — [343max/eero-client](https://github.com/343max/eero-client)

**Python clients**

### Inferences
- No eero integration ships in Home Assistant core. All of them are HACS custom components (inferred from every integration found being a custom repo).
- Homebridge eero plugins and Go clients were not surfaced by the searches run, which suggests they are niche or inactive. This was not confirmed.
- For a 2026 build, `eero-api` (Python) is the most complete, documented and recently live-verified wrapper. The raw HTTP API is simple enough to call directly from any language.
- 343max's client is useful only as a minimal reference for the auth flow.

### Gaps
- The server-side session token lifetime is undocumented. Users report weeks to months in practice, but no source was found to confirm this.
- It is not confirmed whether eero has changed or blocked any endpoint in 2026. No breakage reports were found apart from the long-standing Amazon-login limitation.
- Homebridge, Go and Node client maintenance status was not checked.

## 3. What data is exposed, and which endpoints give which fields?

### Takeaway
The cloud API exposes much of what the app shows. The main resources are:
- **Network:** `/networks/{id}` (settings, health, ISP and WAN, speed tests, DNS, DHCP).
- **Nodes:** `/networks/{id}/eeros` (model, firmware, status, gateway flag, location, client counts, LED, ports and negotiated speeds).
- **Clients:** `/networks/{id}/devices`. Each client has the connected node (`source.location`), wired/wireless `connection_type`, `channel`, `interface.frequency`, signal in dBm (`connectivity.signal`), rx/tx rate info including channel width, usage, profile, paused and guest flags, IP, MAC and manufacturer.
- **History and telemetry:** channel utilization per band and per eero, a neighbouring-network scan, and data-usage and insights history.
- **Other resources:** reservations, port forwards, DDNS, Thread, and eero Plus security and DNS policies.

These are the raw materials for diagnosing weak coverage areas.

### Cited Findings
**Endpoint templates in eero-api** (all relative to `/2.2/` unless noted; source: [eero-api src/eero/api/](https://github.com/fulviofreitas/eero-api/tree/HEAD/src/eero/api)):
- **Nodes:** `eeros/{id}`, `eeros/{id}/connections` (the eero's client connections), `eeros/{id}/ports`, `eeros/{id}/action`, `eeros/{id}/led`, `eeros/{id}/led_cycle`, `eeros/{id}/nightlight/override`, `eeros/{id}/pppoe`, `eeros/{id}/reboot`, `eeros/{id}/support`
- **Network core:** `networks/{id}`, `networks/{id}/eeros`, `networks/{id}/devices`, `networks/{id}/profiles`, `networks/{id}/profiles/{id}/schedules/{id}`, `networks/{id}/settings`, `networks/{id}/speedtest`, `networks/{id}/diagnostics`, `networks/{id}/routing` (served on 2.3), `networks/{id}/reboot`
- **Addressing and Wi-Fi settings:** `networks/{id}/reservations`, `networks/{id}/forwards`, `networks/{id}/guestnetwork`, `networks/{id}/guestnetwork/password`, `networks/{id}/password`, `networks/{id}/subnets_config`, `networks/{id}/multistaticip`, `networks/{id}/ddns/enable|disable`, `networks/{id}/wpa3_per_band`, `networks/{id}/mlo_mode`, `networks/{id}/fast_transition`, `networks/{id}/passpoint/enabled`, `networks/{id}/temporary_flags/hide_5g`, `networks/{id}/power_saving`
- **Backup and failover:** `networks/{id}/backupinternet`, `networks/{id}/backup_access_points` (and connectivity_check, ssid_discovery, rearrange), `networks/{id}/cellular_backup_events`, `networks/{id}/cellular_backup_usage`, `networks/{id}/proxied_nodes`

- **Security and DNS:** `networks/{id}/blacklist`, `networks/{id}/dns_policies/network/blocked|allowed`, `networks/{id}/dns_policies/profiles/...`, `networks/{id}/dns_policies/advanced_content_filter`
- **Thread:** `networks/{id}/thread`
- **Firmware:** `networks/{id}/updates`, `networks/{id}/updates/preferred_update_hour`

**Events, scan and RF telemetry**
- `networks/{id}/app_events` (paged) and `networks/{id}/network_scan` (verified reads).
- `networks/{id}/channel_utilization` with `start`/`end` and optional `busy_threshold`, `eero_id`, `band` and `granularity`. Bands: `band_2_4GHz`, `band_5GHz_low`, `band_5GHz_high`, `band_5GHz_full`, `band_6GHz`.

- Source: [eero-api wiki: API Reference](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/API-Reference.md)

**Live throughput (burst reporter)**
- POSTing to `burst_reporters` requests a live-usage burst. About 12 s later, each device's `usage.down_mbps` and `usage.up_mbps` in the device list are refreshed. **What fulviofreitas/homeassistant-eero exposes as entities** (source: [fulviofreitas/homeassistant-eero](https://github.com/fulviofreitas/homeassistant-eero)):
- Network: connected and guest client counts, public IP, gateway IP, WAN router IP, status, DNS mode, and Thread (network name, channel, PAN ID).
- Speed test: last download and upload results.
- Nodes: per-port connection status and negotiated speed, and firmware installed/latest with release notes.
- Clients: per-client signal strength (dBm, wireless only).

**eero-prometheus-exporter**
- Default tiers are `core`, `extended` and `rf`. Opt-in tiers are per-profile, per-device, per-eero and unverified.
- It covers network health, ISP state, speed tests, DNS, DHCP and WAN modes, 119 capability flags, and per-eero per-band channel, channel width, TX power and utilisation.
- Per device: connection quality, PHY rates, MCS/NSS and packet statistics. eero Plus: entitlements, DNS policies and insights.
- With default tiers it makes about 29 API requests per cycle; the example interval is 120 s. 36 metrics were removed in 4.0.0 for lacking an API source.
- The README says "202 metrics" while the repo description says "90+", so the count is inconsistent.
- Source: [eero-prometheus-exporter](https://github.com/fulviofreitas/eero-prometheus-exporter)

**Thread credentials**
- The Thread endpoint returns credential material: `thread_network_name`, `thread_network_key`, PAN ID and channel. eero-api also exposes `regenerate_thread_credentials` and `update_thread` (including `enable_credential_syncing`). — [eero-api src/eero/api/thread.py](https://github.com/fulviofreitas/eero-api/blob/HEAD/src/eero/api/thread.py); [API Reference](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/API-Reference.md)

### Inferences
- For a coverage-diagnosis tool:
  - Device list: join `source.location` (node), `connectivity.signal` (dBm), `interface.frequency` and `channel`, and rx/tx rate info. This gives a per-room picture of which clients are weak and on which node.
  - `channel_utilization` and `network_scan`: show congestion and neighbouring interference.
  - Node `ports`: show wired-backhaul link speeds.
- For a security tool: `devices` (new or unknown MACs, manufacturer), `blacklist`, `dns_policies`, `members`/`invites` (who has admin), `forwards`, the UPnP and WPA3 settings, and `app_events`.
- The Thread key is a sensitive secret. Any tool that logs raw responses must redact it.

### Gaps
- No field name for mesh backhaul quality could be confirmed in the code inspected: no `mesh_quality_bars`, wireless/wired backhaul flag, or upstream node. The eero app shows this, and the raw `eeros` JSON likely contains it, but it was not verified. It will need to be confirmed by inspecting a live response.
- The exact field names for the app's per-client "connection quality" bars were not confirmed. The exporter claims "connection quality" metrics, but its field mapping is in an unread wiki page.
- The `diagnostics` and `routing` response shapes are not documented. `run_diagnostics` is marked "unverified body shape."
- No evidence was found that the API exposes an explicit topology graph (node-to-node parent links) beyond per-node and per-client fields.

## 4. What can be controlled?

### Takeaway
Through the cloud API you can control essentially everything the app can.
- **Low-risk:** reboot a single eero, run a speed test, pause, block or unblock devices, edit profiles and schedules, toggle guest Wi-Fi.
- **Network-wide settings:** band steering, SQM ("optimize for conferencing and gaming"), UPnP, IPv6, WPA3 per band, MLO mode, fast transition (802.11r), DHCP, DNS, DDNS, reservations, port forwards, Thread, LEDs and nightlight, firmware updates, port and PoE actions.
- Many writes are flagged "unverified." Settings-class writes reboot the network, so they should be done carefully.

### Cited Findings
**Verified actions** (source: [eero-api wiki: API Reference](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/API-Reference.md)):
- `run_speed_test`: POST to the `speedtest` link returns 202. The result appears in `get_speed_tests` about a minute later. Verified 2026-09-20.
- `reboot_eero`: only the targeted node reboots. Verified 2026-09-20.
- `pause_device`: verified, on API version 2.3.
- `block_device` and `unblock_device`: POST and DELETE on `networks/{id}/blacklist`. Verified 2026-10-06.

**Riskier or unverified actions** (same source):
- `reboot_network` "reboots every eero."
- `apply_update` reboots every node.
- `node_action` takes `POWER_CYCLE_ALL_PORTS` or `POWER_CYCLE_ALL_PORTS_AND_REBOOT`.
- `port_action` takes ENABLE/DISABLE_DATA, POE, PORT, PORT_SECURITY, or RESTART_POWER. These action lists come from [eero-api eeros.py](https://github.com/fulviofreitas/eero-api/blob/HEAD/src/eero/api/eeros.py).
- `set_pppoe` returns an encrypted credential blob.

**Settings writes** (via the `settings` link):
- `set_band_steering`, `set_upnp`, `set_ipv6` (writes `ipv6_upstream` and `ipv6_downstream`), `set_wpa3`, `set_wpa3_per_band` (WPA2 / WPA2_WPA3 / WPA3)
- `set_mlo_mode` (disabled / single / multi), `set_sqm`, `set_dhcp`, `set_fast_transition`, `set_passpoint_enabled`, `set_power_saving`, `set_hide_5g`, `set_preferred_update_hour`, `set_guest_network`
- DNS writes, DDNS, subnets and multi-static-IP, secondary WAN, `allow_domain`, `block_domain`, and bedtime schedules
- Source: [eero-api wiki: API Reference](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/API-Reference.md); [Caching-and-Rate-Limits](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Caching-and-Rate-Limits.md)

**Warnings from the eero-api docs**
- "Never retry in a tight loop. A burst of writes appears to queue a burst of reboots."
- The guidance is to read current state first, skip the write if nothing changed, and treat a 200 as "accepted", not as applied. — [eero-api wiki](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/API-Reference.md)
- `set_device_priority` was removed in v8.0.0: "the API never exposed device-level priority; the method returned 200 OK and changed nothing." — [eero-api Troubleshooting](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Troubleshooting.md)

**Home Assistant controls**
- The HA integrations expose these controls as entities: guest network, eero Plus and Labs toggles, pausing profiles and clients, content filters, blocked apps, firmware updates, backup networks, reboot and port actions, and the run-speed-test button. — [schmittx](https://github.com/schmittx/home-assistant-eero); [fulviofreitas/homeassistant-eero](https://github.com/fulviofreitas/homeassistant-eero)

### Inferences
- A safe diagnostic tool should be read-mostly. Only `run_speed_test`, `reboot_eero` and `create_burst_reporter` are verified, low-blast-radius writes suitable for automation.
- A 200 response from settings writes does not prove the setting changed, so tools should re-read state afterwards.

### Gaps
- No source documented a per-client steering or "kick to another node" action. It appears not to exist.
- There appears to be no per-client band or node pinning. This was not confirmed.

## 5. Local and LAN interfaces (SNMP, syslog, UPnP, port mirroring, SSH, web UI) and Matter/Thread/Zigbee

### Takeaway
No source found any local management surface: no local web UI, LAN API, SSH, SNMP, syslog export or port mirroring. All management goes through the cloud. The LAN-visible features that do exist are standard network services:
- UPnP (togglable)
- IPv6
- DHCP and DNS
- Thread border router (the Thread network's credentials can be read through the cloud API)

No sources describe any exposed Zigbee or Matter control API.

### Cited Findings
- eero has "no web admin panel," and management happens through the mobile app. This comes from a third-party guide, not eero. — [busuk.org eero login guide](https://busuk.org/router/eero/)
- eero community users have requested a web interface. The thread shows only requests and closed duplicates. — [eero Community: web interface](https://community.eero.com/t/h4thvv/web-interface)
- A 2020 blog describes eero management as cloud-only, with no local management interface; the nodes call out to a cloud API. This is older, flagged as 2020. — [obriencj: The eero6 Mistake](https://obriencj.preoccupied.net/blog/2020/11/27/the-eero6-mistake/)
- A 2022 HN commenter said eero has no SNMP ("they are not going to add SNMP, no matter how many times you ask") and no decent network monitoring via app or API. Another user used an external switch SPAN port for traffic visibility. This is older, flagged as 2022. — [Hacker News](https://news.ycombinator.com/item?id=30982044)
- A 2026 how-to says the consumer app has no traditional syslog console. For packet captures, DNS query logs, firewall logs or syslog export, it says you need a different router or a separate monitoring appliance. — [ROIhacks: How to check logs on your eero network](https://roihacks.com/how-to-check-logs-on-your-eero-network/)
- A dashboard project's feature request for logging also reflects the lack of logs. — [Dashboard_EERO issue #59](https://github.com/EnricoFlammini/Dashboard_EERO/issues/59)
- UPnP and IPv6 are standard settings toggled in the app, and also via the API's `set_upnp` and `set_ipv6`. — [XDA: 6 eero settings](https://www.xda-developers.com/change-these-settings-optimize-your-eero-router/); [eero-api API Reference](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/API-Reference.md)
- eero 6-generation devices act as Thread border routers for Matter devices, and the Pro 6E datasheet lists Thread border router support. — [BusinessWire 2022 launch](https://www.businesswire.com/news/home/20220323005362/en); [eero Pro 6E datasheet](https://thekentongroup.com/wp-content/uploads/2024/10/eeroPro6E-datasheet.pdf)
- The cloud API exposes Thread state and credentials, can enable or disable Thread, and has a credential-sync flag. — [eero-api thread.py](https://github.com/fulviofreitas/eero-api/blob/HEAD/src/eero/api/thread.py)

### Inferences
- For deeper local visibility, the practical options are:
  - Passive LAN tools: ARP and mDNS scans, and Wi-Fi scanning from clients for RSSI heatmaps.
  - Putting a managed switch with port mirroring between eero and LAN.
  - Running eero in bridge mode behind a router that supports SNMP and syslog.
- The eero cloud API remains the only source of eero's own per-node and per-client radio view.
- Thread credentials from the API could let a separate Thread border router (e.g. HA OpenThread) join the eero Thread network. This was not verified.

### Gaps
- No official eero statement was retrieved that explicitly says "SNMP/syslog/SSH are not supported." The support site was unreachable, and the conclusion rests on secondary sources plus the absence of any documentation.
- No source covered Zigbee hub features (some eero models had Zigbee via Alexa integration) or any API for them.
- Matter controller exposure was not found.
- Whether UPnP-IGD on eero exposes useful WAN or status data to LAN clients was not checked.

## 6. Terms of service, rate limits, ban risk, and recommended practices

### Takeaway
- No eero ToS clause specifically about third-party API clients was retrieved.
- Every unofficial project labels itself unaffiliated and reverse-engineered, so it can break without notice.
- The documented practical ceiling is about 100 requests per minute, with HTTP 429 and `Retry-After` beyond that.
- No reports of account bans were found.
- Recommended practice:
  - Use a dedicated email or phone admin account, invited to the network, rather than your owner or Amazon account.
  - Poll every 2–5 minutes, with longer intervals for slow-changing data.
  - Cache and back off.
  - Never retry writes in a loop.
  - Treat the token as a full-admin secret.

### Cited Findings
- "The Eero Cloud API tolerates roughly 100 requests/minute. Exceeding it returns HTTP 429." The SDK exposes `retry_after` from `Retry-After` and never retries a 429 or any write itself. Its default cache TTL is 60 s, and it advises raising the TTL for polling workloads and batching reads. — [eero-api wiki: Caching and Rate Limits](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Caching-and-Rate-Limits.md)
- The login endpoint can itself rate-limit, raising `EeroRateLimitException`. Login error codes include `error.login.blocked` and `error.too.many.resends`. — [eero-api wiki: Authentication](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Authentication.md)
- Polling defaults in maintained tools:
  - HA integration: 300 s fast tier (minimum 60 s), hourly for activity, daily for firmware and Thread. — [fulviofreitas/homeassistant-eero](https://github.com/fulviofreitas/homeassistant-eero)
  - Prometheus exporter: example interval 120 s, about 29 requests per cycle. — [eero-prometheus-exporter](https://github.com/fulviofreitas/eero-prometheus-exporter)
- The dedicated admin account workaround (create an email or phone account and invite it as admin) is the standard advice across tools. — [schmittx README](https://github.com/schmittx/home-assistant-eero); [schmittx issue #77 instructions referenced in README](https://github.com/schmittx/home-assistant-eero/issues/77#issuecomment-1960875926); [eero-api Troubleshooting](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Troubleshooting.md)
- Disclaimers: "not affiliated with or endorsed by Eero" ([eero-api](https://github.com/fulviofreitas/eero-api)), and the API was obtained "by intercepting the traffic of the eero app" ([343max](https://github.com/343max/eero-client)).
- eero-api's transport attaches the token only to the exact API host over HTTPS, refuses redirects, and rejects caller-supplied credential headers. These are useful patterns for anyone writing their own client. — [eero-api wiki: Authentication](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Authentication.md)

### Inferences
- A tool that polls `networks`, `eeros` and `devices` every 2–5 minutes stays far below about 100 requests per minute.
- Heavier calls (channel utilization, insights, data usage) can run every 15–60 minutes.
- The main risk is breakage, not bans: endpoint changes, or a possible future forced move to Amazon-only login.
- A leaked token gives full admin control: it can read Wi-Fi passwords and Thread keys and reboot the network. Store it in a keyring and redact logs.

### Gaps
- The eero Terms of Service text was not retrieved (eero.com was blocked), so whether reverse-engineered access is explicitly prohibited is unconfirmed.
- No first-hand reports of account suspension for API use were found, but the absence of reports is not proof of zero risk.
- The 100 requests/minute figure is the SDK author's observation, not an eero-published limit.

## 7. The eero app's own diagnostic features, and which are only in the app

### Takeaway
The app adds network settings and "eero Labs" toggles: band steering, local DNS caching, "Optimize for conferencing and gaming" (SQM), and WPA3, with newer settings like MLO on Wi-Fi 7 models. Most of these toggles are also exposed through the cloud API. App-only, from a home user's view: polished visualizations such as connection-quality presentation, guided troubleshooting, and support chat. Their underlying data appears to come from the same API (`diagnostics`, `insights`, `channel_utilization`).

### Cited Findings
- eero Labs holds experimental features, described as "in beta, and still in development." It includes band steering, local DNS caching, automatic QoS for conferencing and gaming, and WPA3. This source is from 2020. — [McCann Tech eero setup guide (2020)](https://evanmccann.net/blog/2020/8/eero-setup-guide)
- The Pro 6E datasheet labels WPA3 and "Optimize for conferencing and gaming" as eero Labs features. — [eero Pro 6E datasheet](https://thekentongroup.com/wp-content/uploads/2024/10/eeroPro6E-datasheet.pdf)
- Band steering encourages capable devices onto 5 GHz. "Optimize for conferencing and gaming" is SQM; it helps when calls lag during heavy use and may lower peak speed-test results. Disabling local DNS caching can fix some login-loop glitches. — [XDA: 6 eero settings](https://www.xda-developers.com/change-these-settings-optimize-your-eero-router/); [rottenwifi summary](https://rottenwifi.com/get-a-better-more-stable-connection-by-changing-these-6-eero-settings/)
- A community thread discusses using these settings to improve speed. — [eero Community: Improving speed](https://community.eero.com/t/q6hxdkq/improving-speed)
- The API equivalents exist: `set_band_steering`, `set_sqm`, `set_wpa3` / `set_wpa3_per_band`, `set_ipv6`, `set_upnp`, `set_mlo_mode`, `set_fast_transition`, and the DNS settings including caching. Diagnostics are exposed via `get_diagnostics` / `run_diagnostics` (device and symptom parameters), along with `get_network_scan`, `get_channel_utilization` and `get_app_events`. — [eero-api API Reference](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/API-Reference.md)
- The HA integrations control "Eero Labs features" as switches. — [schmittx README](https://github.com/schmittx/home-assistant-eero)
- In the app, Business Insight-style dashboards are owner-only. — [eero Insight for Business](https://support.eero.com/hc/en-us/articles/19653076310555-eero-Insight-for-Business)

### Inferences
- `run_diagnostics(device, symptom)` probably backs the app's guided "troubleshoot a device" flow. This is inferred from the parameter names and has not been verified.
- Because most app features map onto API resources, a custom tool can reproduce, and exceed, the app's coverage diagnostics by storing history the app doesn't keep: per-client dBm over time per node, plus channel utilization.

### Gaps
- The 2026 eero Labs lineup (e.g. on eero Pro 7, Max 7 and Outdoor 7) was not retrieved, because the eero support pages were blocked.
- How the app computes its "connection quality" bars, and how that maps to dBm or PHY rate, was not found.
- Whether the eero 7-series adds any new diagnostics (e.g. RF spectrum or per-node interference views) was not confirmed.
- Whether local DNS caching is still a Labs toggle in 2026 or has graduated to a standard setting was not confirmed.
