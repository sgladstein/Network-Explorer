# Mine eero's cloud API, then measure rooms

eero gives home users **no official API**, but the undocumented cloud API behind its mobile app (`api-user.e2ro.com`) is now well mapped by maintained open-source clients. That API exposes almost everything the app shows. For each client you get the node it is attached to, its band, channel, signal in dBm and PHY rates. For each node you get firmware, ports and negotiated link speeds. Across the network you get channel utilization, a neighbour scan, speed tests and usage history. You can also change most settings. What eero cannot tell you is what a room *feels like* from the client side, who is talking to whom on the LAN, or what traffic leaves the house. eero has no SNMP, syslog, port mirroring, local web UI or internal VLANs. So a useful tool has to fuse three data sources. The first is eero cloud polling, the authoritative node and client view. The second is LAN discovery (ARP, mDNS, SSDP, nmap) for identity and exposure. The third is client-side measurement (walk surveys and fixed room probes running iperf3, ping and nl80211 stats) for coverage diagnosis. Deep traffic and IDS visibility needs extra hardware: a SPAN-capable switch, or eero in bridge mode behind a firewall. The collector layer is effectively solved by projects like Dashboard_EERO, eeroVista and the `eero-api` Python SDK. The open gap is the join: no project yet combines eero node data with active discovery, floor-plan surveys and a natural-language "why is this room slow" layer. That join is where a new tool earns its keep.

## The unofficial app API exposes nearly everything, but only through the cloud

### Official channels are closed to hobbyists

eero has three official data routes, and none suits a home builder. The **Data Portability API** is OAuth 2.0 and read-only. It is framed around EU customers' data rights and open only to third parties that complete a security assessment and sign an NDA, after which "eero will share the full documentation with you via email" ([eero Data Portability Onboarding](https://support.eero.com/hc/en-us/articles/40180105962139-eero-Data-Portability-Third-Party-Onboarding); [eero Data Portability](https://support.eero.com/hc/en-us/articles/40180112699931-eero-Data-Portability)). Its timing and EU scope suggest it is eero's way of complying with the EU Data Act, which has applied since September 2025 ([ayedo](https://ayedo.de/en/data-act/)). eero's pages do not say so; that is an inference. **eero Insight** is a web portal for eero Business owners with no documented API ([eero Insight for Business](https://support.eero.com/hc/en-us/articles/19653076310555-eero-Insight-for-Business)). Its "Insight Exchange" APIs for reboots, topology and outage data are ISP-partner only ([eero for ISPs](https://eero.com/isp); [BusinessWire 2021](https://www.businesswire.com/news/home/20211025005257/en)). The third route, the Data Management download at account.eero.com, is a one-off export rather than a live feed.

### The app API is simple, passwordless and well wrapped

Every hobbyist tool talks to the same mobile-app backend at **`https://api-user.e2ro.com/2.2`**, with a few resources on `/2.3` ([eero-api const.py](https://github.com/fulviofreitas/eero-api/blob/HEAD/src/eero/const.py)). Login is passwordless. You POST an email or phone number to `/2.2/login`, receive a `user_token`, and POST the one-time code to `/2.2/login/verify`, which turns that same token into a verified session. The token travels as an `X-User-Token` header or an `s=` cookie. There is no refresh token: the server returns 401 `error.session.refresh` when it wants a refresh, and "there is no client-side session expiry" ([eero-api wiki: Authentication](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Authentication.md)). The original reverse-engineering was done "by intercepting the traffic of the eero app" ([343max/eero-client](https://github.com/343max/eero-client)). One limitation shows up in every project: **accounts that sign in with Amazon do not work.** The standard workaround is to create a separate email or phone eero account and invite it as a network admin ([schmittx/home-assistant-eero](https://github.com/schmittx/home-assistant-eero); [eero-api Troubleshooting](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Troubleshooting.md)). That workaround is also good security practice.

The clear choice for a 2026 build is **fulviofreitas/eero-api**. It is an async Python 3.12+ SDK at v8.4.1, with roughly 615 commits, keyring credential storage, and a release cadence of four versions in October 2026 alone ([eero-api](https://github.com/fulviofreitas/eero-api); [CHANGELOG](https://github.com/fulviofreitas/eero-api/blob/HEAD/CHANGELOG.md)). A CLI (eeroctl), a Prometheus exporter, a Home Assistant integration, a Rust port (rusteero) and a device-change detector have grown up around it. Go (eero-go) and JavaScript clients also exist ([eero-go](https://github.com/arvarik/eero-go); [eero-js-api](https://github.com/bbernstein/eero-js-api)). The older 343max client is now useful only as a minimal reference for the auth flow; its last push was in 2024.

### What the data actually contains

The table below summarises the resources that matter for a connectivity and security tool. Endpoints come from the eero-api source and wiki. Client and node field names come from the schmittx integration's parsers ([eero-api src/eero/api](https://github.com/fulviofreitas/eero-api/tree/HEAD/src/eero/api); [API Reference](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/API-Reference.md); [schmittx client.py](https://github.com/schmittx/home-assistant-eero/blob/HEAD/custom_components/eero/api/client.py); [schmittx eero.py](https://github.com/schmittx/home-assistant-eero/blob/HEAD/custom_components/eero/api/eero.py)).

| Resource | Key contents | Use in a tool |
|---|---|---|
| `networks/{id}/devices` | `source.location` (serving node), `connection_type`, `interface.frequency`, `channel`, `connectivity.signal` ("-NN dBm"), rx/tx rate info incl. channel width, IP, MAC, manufacturer, hostname, `is_guest`, `paused`, `usage` | Per-client coverage view, inventory, topology |
| `networks/{id}/eeros`, `eeros/{id}/ports` | Model, firmware, gateway flag, location, client count, status, update and support-expiry status, per-port link and negotiated speed | Node health, wired-backhaul check, firmware audit |
| `networks/{id}/channel_utilization` | Busy time per band (2.4, 5 low/high, 6 GHz) per eero, with time range and granularity | Congestion vs coverage diagnosis |
| `networks/{id}/network_scan` | Neighbouring networks | Co-channel interference |
| `burst_reporters` | Triggers ~12 s live refresh of per-device `down_mbps`/`up_mbps`; max one per minute | Live "who is using bandwidth" |
| `speedtest`, `insights`, `transfer`, `app_events` | Speed-test history, usage history, event log | ISP vs Wi-Fi separation, timeline |
| `forwards`, `reservations`, `settings`, `members`, `blacklist`, `dns_policies` | Port forwards, UPnP/WPA3/IPv6/DNS state, admin list, blocked devices | Security audit |
| `networks/{id}/thread` | Thread network name, **network key**, PAN ID, channel | Matter/Thread integration (sensitive) |

The maintained Prometheus exporter turns this into per-eero, per-band channel, width, TX power and utilization metrics. It also produces per-device connection quality, PHY rates and MCS/NSS. It makes about 29 API calls per cycle at an example 120 s interval ([eero-prometheus-exporter](https://github.com/fulviofreitas/eero-prometheus-exporter)). Two important gaps remain. **No field for mesh backhaul quality or node-to-node parent links has been confirmed** in any client's code, even though the app displays backhaul status. And the formula behind the app's "connection quality" bars is unknown. eeroVista advertises a mesh topology view ([eeroVista](https://github.com/Yeraze/eeroVista)), so the raw `eeros` JSON probably contains upstream data. Anyone building a topology map should first dump a live response and confirm it.

### Control exists, but writes are hazardous

The API can change essentially everything the app can. That includes band steering, SQM ("optimize for conferencing and gaming"), UPnP, IPv6, WPA3 per band, MLO, 802.11r, DHCP, DNS, reservations, forwards, guest Wi-Fi, LEDs, Thread, firmware and even PoE port actions. Only a handful of writes are live-verified: **speed test, single-node reboot, pause device, and block/unblock** ([eero-api API Reference](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/API-Reference.md)). The SDK's own warnings shape any automation design. Settings writes reboot the network, and "a burst of writes appears to queue a burst of reboots." A 200 response means "accepted", not "applied". One method, `set_device_priority`, "returned 200 OK and changed nothing" until it was removed ([Troubleshooting](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Troubleshooting.md)). No per-client steering, "kick to another node" or band pinning action exists. A diagnostic tool should therefore be **read-mostly**. It should automate only the verified low-blast-radius actions, and it should re-read state after any write.

### Rate limits, risk and the absence of anything local

The SDK author observes a ceiling of roughly **100 requests per minute**, with HTTP 429 and `Retry-After` beyond that. Login can be rate-limited separately ([Caching and Rate Limits](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Caching-and-Rate-Limits.md)). The maintained HA integration polls core data every 300 s, activity hourly and firmware/Thread daily ([fulviofreitas/homeassistant-eero](https://github.com/fulviofreitas/homeassistant-eero)). eeroVista polls devices every 30 s ([eeroVista](https://github.com/Yeraze/eeroVista)). Either fits under the ceiling. A 60–120 s device poll with 15–60 minute intervals for heavy history calls is a sensible middle ground. No reports of account bans were found. The real risk is breakage: undocumented endpoints can change, and a forced move to Amazon-only login would strand every tool. eero's terms of service could not be retrieved, so whether they prohibit this use is unknown. On the local side, no source found any SNMP, syslog, SSH or LAN management API. eero has "no web admin panel" ([busuk.org](https://busuk.org/router/eero/)), and a 2026 how-to says log or packet visibility requires a different router or a separate appliance ([ROIhacks](https://roihacks.com/how-to-check-logs-on-your-eero-network/)). **The cloud API is the only source of eero's own radio view.** Everything else must come from devices you place on the LAN yourself.

## Coverage diagnosis needs client-side measurements eero cannot supply

### eero sees the link from the access point; users feel it at the client

eero's per-client dBm, node and band are a good starting point. But they cannot tell you whether a video call stutters in the back bedroom, whether that room is starved by backhaul, or whether a microwave is the culprit. That requires measuring from the client side, and here operating systems differ sharply. **Linux** exposes nearly everything through nl80211. `iw station dump` gives averaged RSSI and cumulative `tx_retries` and `tx_failed`, and `iw survey dump` gives channel active and busy time, from which utilization ≈ Δbusy/Δactive ([Debian station_info](https://manpages.debian.org/wheezy/linux-manual-3.2/struct_station_info.9.en.html); [ath10k list](https://lists.infradead.org/pipermail/ath10k/2015-June/005469.html); [TelecomHall](https://www.telecomhall.net/t/high-channel-utilization-isn-t-always-a-problem/33620)). There are caveats: some firmware reports zero retries or resets survey counters ([kernel patchwork](https://patchwork.kernel.org/patch/11504903); [LKML](https://lkml.iu.edu/hypermail/linux/kernel/2010.3/03630.html)). **macOS** removed the `airport` CLI in 14.4, and `wdutil` needs sudo and has been reported to redact SSID and BSSID ([Jamf community](https://community.jamf.com/t5/jamf-pro/collecting-active-ssid-with-macos-sonoma-14-4-and-later/m-p/311680)). CoreWLAN returns RSSI, noise and BSSID only to a signed app with Location Services permission, which rules out a headless launchd daemon ([macwifi](https://jaisonerick.github.io/macwifi/); [DEV Community](https://dev.to/jaisonerick/reading-wi-fi-data-from-go-on-macos-after-apple-removed-airport-19g)). **Windows** reports only a 0–100 `wlanSignalQuality` that maps linearly from −100 to −50 dBm, so it clips every strong signal ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/wlanapi/ns-wlanapi-wlan_association_attributes)). **Android** limits foreground apps to 4 scans per 2 minutes, though apps can passively receive scans the platform runs anyway ([Android Developers](https://developer.android.com/develop/connectivity/wifi/wifi-scan)). **iOS** has "no official or supported way" to read RSSI ([Apple Developer Forums](https://developer.apple.com/forums/thread/835163)).

The design implication is clear. Active tests (ping latency, jitter and loss to the gateway and the internet, plus iperf3 throughput to a *wired* LAN host) work on every platform and measure what users actually feel. RSSI, noise, PHY rate, retries and busy time are platform-specific extras that explain *why*. iperf3 against a wired host isolates Wi-Fi and backhaul from the ISP. Comparing it with eero's internet speed test separates "my mesh" from "my provider".

### Walk surveys are easy to build; reading Wi-Fi metrics is the hard part

Every open-source heatmapper uses the same pattern: load a floor-plan image, click your position, record Wi-Fi stats and optionally iperf3, then interpolate. **hnykda/wifi-heatmapper** is the most current. It is MIT-licensed, runs on macOS, Windows and Linux, takes about 2 s per point in signal-only mode, stores surveys as plain JSON and even ships an optional MCP server ([wifi-heatmapper](https://github.com/hnykda/wifi-heatmapper)). Its history shows where the effort goes. `wdutil` parsing broke on macOS 15.0–15.2, and `netsh` output is localized, so the project moved to a native macOS helper. **jantman/python-wifi-survey-heatmap** is Linux-only and inactive. It still pioneered a useful "frequency" heatmap that shows where band steering fails and clients fall back to 2.4 GHz ([jantman](https://github.com/jantman/python-wifi-survey-heatmap)). Building a custom surveyor means writing a platform adapter layer: nl80211 on Linux, a signed CoreWLAN helper on macOS, the Native Wifi API rather than `netsh` on Windows, `WifiInfo` on Android, and active tests only on iPhones. For an MVP it is cheaper to **import wifi-heatmapper's JSON** than to rebuild that UX.

The academic name for turning sparse readings into a map is *radio map estimation*. The literature runs from kriging and Gaussian processes to GANs and 3D Gaussian splatting ([Romero & Kim](https://www.alphaxiv.org/abs/2202.03269); [RADIANCE](https://www.alphaxiv.org/abs/2308.10584); [RadCloudSplat](https://www.alphaxiv.org/abs/2502.12686)). Two ideas transfer directly to a hobby tool. First, Gaussian-process regression with a Matérn kernel produces a standard-deviation map alongside the mean, telling the user *where to measure next* ([arXiv 2610.40723](https://www.alphaxiv.org/abs/2610.40723)). Second, indoor RSS varies over time as well as space ([arXiv 2402.05083](https://www.alphaxiv.org/abs/2402.05083)), so each point needs several timestamped samples. The highest-value refinement is to interpolate **per eero BSSID or band**, not just "the network". That shows where each node's cell ends, which is exactly the input needed to decide where to move or add a node.

### Fixed room probes catch what one-time surveys miss

A walk survey is a snapshot. Evening congestion, roaming flaps and intermittent interference need a probe that stays in the problem room. That can be a Raspberry Pi with a well-supported MediaTek adapter, or a WLAN Pi, collecting `iw` station and survey dumps and ping every 1–5 minutes, plus a short iperf3 run every 15–30 minutes to a wired server. Results go to Prometheus or InfluxDB. The WLAN Pi's **profiler** adds something no other tool does. It advertises a fake AP and parses clients' association requests to reveal spatial streams, supported bands and 802.11k/v/r support, which exposes problems that are really *client* limitations ([wlanpi-profiler](https://github.com/WLAN-Pi/wlanpi-profiler)). ESP32 boards in promiscuous mode are cheap RSSI and frame-count sensors ([ETHERFOG](https://github.com/invpe/ETHERFOG)). But most variants see only 2.4 GHz, and none of the projects found compute true airtime or export Prometheus metrics. No existing project combines Pi probes with eero node mapping.

### Separating causes from data

eero's own placement guidance is the baseline. It says to place nodes 20–30 ft apart and no more than 50 ft, in the open, and to put a node *halfway* to a dead zone rather than inside it ([eero placement](https://eero.com/support/articles/where-should-i-place-my-eeros)). Radio controls are minimal. Channels and power are automatic. Client Steering "does not guarantee that a device will choose the 5 GHz or 6 GHz bands nor the closest eero" ([eero advanced features](https://support.eero.com/hc/en-us/articles/207613326)). 802.11v steering is advisory, so clients make the final roaming decision ([Access Agility](https://support.accessagility.com/hc/802.11k-802.11r-and-802.11v)). A tool's recommendations should therefore be about placement, backhaul and client fixes, not channel plans. The heuristic table below draws the research together. Its thresholds are starting points to calibrate on real hardware, not sourced standards.

| Diagnosis | Signature in the data | Typical fix |
|---|---|---|
| Coverage / placement | RSSI below roughly −70 dBm, low PHY rate, throughput tracks RSSI | Move a node toward the room, or add one |
| Wi-Fi congestion | Good RSSI (−50 to −65) but high retries, high busy %, many same-channel neighbours in `network_scan`, worse at peak hours | Wired backhaul, 5/6 GHz clients, fewer 2.4 GHz devices |
| Non-Wi-Fi interference | Brief retry/noise spikes, busy % rises without matching frames | Confirm with a 2.4 GHz spectrum analyser; move the source |
| Weak backhaul | Strong RSSI and high PHY rate near a satellite, but iperf3 far below PHY rate for every client on that node | Ethernet or MoCA backhaul; reposition the satellite |
| Sticky client | Associated BSSID is a far node while a passive scan shows a nearer eero 10+ dB stronger | Forget and rejoin; check k/v/r support |
| Client limitation | Profiler shows one spatial stream, no 5/6 GHz, or no k/v/r | Replace the adapter or device |

eero's API supplies the right-hand side of several rows: serving node, band, signal, `channel_utilization`, `network_scan`, and port speeds that reveal whether backhaul is really wired. Client probes supply the rest. Spectrum analysis matters mainly for 2.4 GHz mysteries. A MetaGeek Wi-Spy or an RF Explorer sees microwaves and Bluetooth that Wi-Fi chipsets cannot ([Wi-Spy datasheet](https://data.kommago.nl/files/pdf/80834_MetaGeek-Wi-Spy-Datasheet.pdf); [Georgia Libraries RF Explorer](https://galibtech.georgialibraries.org/emerging/tech-loaner-kits/tlk-options/wifi-expansion-kit/rf-explorer)). On 5 and 6 GHz, most interference is neighbours' Wi-Fi, which an ordinary scan already reveals.

## Discovery and traffic visibility stop at eero's flat LAN and NAT

### Inventory: combine eero's list with active and passive probes

No single technique finds every device. **ARP sweeps** (`arp-scan`, `nmap -sn`) find any IPv4 host on the segment, even ones that drop ICMP ([arp-scan](https://github.com/royhills/arp-scan); [Nmap host discovery](https://nmap.org/book/man-host-discovery.html)). Passive listeners add identity. mDNS (`_airplay._tcp`, `_googlecast._tcp`, `_hap._tcp`) names Apple, Chromecast and HomeKit gear, SSDP device descriptions give manufacturer and model, and NetBIOS/LLMNR give Windows hostnames ([python-zeroconf](https://github.com/python-zeroconf/python-zeroconf); [UPnP Device Architecture](https://openconnectivity.org/developer/specifications/upnp-resources/upnp/)). nmap `-O -sV` adds OS and services. eero bridges all nodes into one broadcast domain, so a single wired box can sweep the whole main LAN; the guest network is isolated. The isolation runs both ways, though: **LAN scanning cannot tell which node a client is attached to**. That comes only from eero's `source.location`. The topology map must therefore be a join of the eero device list (MAC, node, wired/wireless, band, signal) with scan data (IP, hostname, mDNS services, OS) keyed on MAC. Wired devices behind an unmanaged switch will appear attached to their eero node.

**MAC randomization is the biggest data-quality problem.** Android 10+ uses a per-SSID random MAC by default, and iOS 18 added an optional rotating address ([purple.ai](https://www.purple.ai/en-us/blogs/randomizzazione-dei-mac-101); [Ubiety](https://ubiety.notion.site/What-is-Private-Address-or-Randomized-MAC-Address-1f3a385f423381bb9e76e4ce2e2cf063)). The result is duplicate "new" devices and broken presence tracking. The locally-administered bit (second hex digit 2, 6, A or E) reliably flags these addresses ([RFC 7042](https://www.rfc-editor.org/rfc/rfc7042)). A robust inventory should flag them, key devices on a composite of eero device ID, hostname, mDNS name and fingerprint, and tell the user to disable rotation for devices they want tracked. IPv6 adds a second problem. Sweeping a /64 is infeasible and privacy addresses rotate ([RFC 8981](https://www.rfc-editor.org/rfc/rfc8981)), so discovery relies on ff02::1 pings, the neighbour cache, passive NDP and mDNS, with the MAC as the join key.

Among off-the-shelf tools, **NetAlertX** leads. It has about 7.4k stars and monthly releases through 2026, with ARP, Pi-hole, DHCP-lease, UniFi and SNMP plugins, Apprise alerts to 80+ services, Prometheus export and a Home Assistant add-on ([NetAlertX](https://github.com/netalertx/NetAlertX)). Its v26 line broke compatibility, enough that some catalogs froze a legacy build ([BigBear community](https://community.bigbeartechworld.com/t/netalertx-legacy-v26-split-in-bigbearuniversal-apps/5246)). **It has no eero importer.** A plugin that pulls eero's device list would be a high-leverage contribution in its own right. WatchYourLAN is a lighter Go alternative whose last release was in September 2025 ([WatchYourLAN](https://github.com/aceberg/WatchYourLAN)). Fing Agent now requires a paid subscription ([Fing help](https://help.fing.com/hc/en-us/articles/14429872073244)).

### Monitoring: probes from the LAN plus a slow eero poller

With no SNMP, SNMP-centric NMS tools like LibreNMS or Zabbix can monitor your own hosts but not the eero nodes. The workable stack is a wired Pi or mini PC running Prometheus with blackbox_exporter, which sends ICMP to each eero node's LAN IP, the gateway, the ISP hop and 1.1.1.1. Add DNS probes, a speed-test exporter, and Smokeping or Uptime Kuma 2.0 for latency distributions and alerting ([blackbox_exporter](https://github.com/prometheus/blackbox_exporter); [SmokePing](https://oss.oetiker.ch/smokeping/); [Linuxiac on Uptime Kuma 2.0](https://linuxiac.com/uptime-kuma-2-0-arrives-with-mariadb-support-modern-ui-refresh/)). Pinging each node from a wired host gives a rough per-node backhaul health signal. An eero API exporter supplies the per-node and per-client radio metrics.

### Traffic: four options, each with a blind spot

eero has no port mirroring, so every route to traffic visibility involves trade-offs. The table compares them.

| Option | What you see | What you lose or miss |
|---|---|---|
| Pi-hole / AdGuard Home as eero custom DNS | All DNS queries; NetAlertX can import its clients | eero Plus filters must be off; queries can appear from the gateway IP until Local DNS Caching is disabled ([Pi-hole discourse](https://discourse.pi-hole.net/t/majority-of-traffic-through-one-client-eero-settings/12536)); DoH/DoT and IPv6 resolvers bypass it |
| eero in bridge mode behind OPNsense/pfSense/Firewalla | Full per-device flows, NetFlow, ntopng, Suricata, DNS enforcement, VLANs | Profiles ([eero](https://support.eero.com/hc/en-us/articles/210819583-Do-Profiles-work-in-bridge-mode)), reservations, port forwarding, custom DNS and most eero Plus features |
| SPAN port on a managed switch between modem and eero | All internet-bound traffic, WAN-side IDS | Post-NAT: no per-device attribution; no intra-LAN traffic |
| Inline two-NIC Linux bridge between modem and eero | Same as SPAN, with optional inline blocking | Same blind spots; adds a point of failure |

eero's own bridge-mode documentation is inconsistent. One version of the support article lists custom DNS, UPnP and most eero Plus features as lost. A newer version lists WAN configuration, local DNS caching, DDNS, MLO, reservations and port forwarding. Both agree that radio features (DFS, client steering, WPA3) survive ([eero bridge-mode features](https://eero.com/support/articles/what-features-do-i-lose-if-i-put-my-eeros-in-bridge-mode); [support article 115000825206](https://support.eero.com/hc/en-us/articles/115000825206)). Builders should test on their own firmware. No option sees Wi-Fi-to-Wi-Fi traffic in router mode, because eero switches it internally. Only host agents would. One practical trick fixes Pi-hole's missing hostnames: pull device names from the eero API and write them into Pi-hole's hosts list, relying on eero reservations for stable IPs ([engineered.at](https://engineered.at/articles/fixing-some-niggles-between-eero-pihole)).

For analysis hardware, ntopng installs from ntop's arm64 repo on a Pi and needs an SSD because it writes heavily ([ntop installation](https://www.ntop.org/software-installation/); [Netgate forum](https://forum.netgate.com/post/1116941)). Independent Pi 5 IDS benchmarks do not exist. The only figure found, about 300 Mbps for stock Suricata before drops, is vendor marketing ([HookProbe](https://dev.to/hookprobe/suricata-vs-zeek-vs-napse-choosing-the-best-edge-ids-for-raspberry-pi-4hmm)). A sensible tiering puts ntopng plus Pi-hole on a Pi 4, ntopng plus Suricata *or* Zeek on an 8 GB Pi 5 with NVMe, and an x86 N100-class mini PC with two NICs for Zeek plus Suricata at gigabit speeds.

## Hardening eero means working around a flat LAN and paywalled DNS

### The built-in baseline is decent but shallow

eero handles the basics. Firmware updates are automatic and cannot be disabled, though you can set a preferred hour ([eero updates](https://eero.com/support/articles/how-do-eeroos-updates-work); [Android Central](https://www.androidcentral.com/can-you-stop-eero-auto-updating-its-software)). Security updates do not require eero Plus ([eero Plus cost](https://support.eero.com/hc/articles/115002904283-How-much-does-eero-Plus-cost)). WPA3 is available, but on 2.4 and 5 GHz only in *transition mode*, because legacy clients "still need to be able to connect using WPA2" ([eero blog](https://blog.eero.com/eero-now-supports-wpa3)). That means passphrase strength still matters and WPA2-only clients stay vulnerable to deauthentication. The 6 GHz band requires WPA3 ([Ezurio](https://www.ezurio.com/support/faqs/in-6ghz-band-is-wpa3-able-to-run-in-transition-mode)). The only published eeroOS CVE found is **CVE-2023-5324**, an Ethernet-interface DoS in eeroOS ≤ 6.16.4-11 rated CVSS 6.5 ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2023-5324)). eero has no public PSIRT page that the research could find.

Three gaps define the hardening work. First, **UPnP is enabled by default** ([eero advanced features](https://support.eero.com/hc/en-us/articles/207613326-What-advanced-features-does-eero-support)), so any compromised IoT device can open inbound port mappings. Turning it off and adding explicit forwards is the single cheapest high-value change. It can be done in the app or via the API's `set_upnp`. Second, **there are no internal VLANs or extra SSIDs**. eero's VLAN setting is for ISP WAN tagging only, and Firewalla staff confirm there is no SSID-to-VLAN mapping ([Best Buy Q&A](https://www.bestbuy.com/site/questions/eero-max-7-tri-band-mesh-wi-fi-7-router-1-pack-white/10104527?page=2); [Firewalla community](https://help.firewalla.com/hc/en-us/community/posts/52619301261075-Eero-Pro-7-in-bridge-mode-can-Firewalla-manage-multiple-SSIDs-mapped-to-VLANs)). Third, the DNS-based protections (threat blocking, ad blocking, content filters) are part of **eero Plus at $9.99/month or $99.99/year** in the US ([eero Plus cost](https://support.eero.com/hc/articles/115002904283-How-much-does-eero-Plus-cost)). They are mutually exclusive with custom DNS: you must switch off Advanced Security, ad blocking and all filters before eero will accept a custom resolver ([eero custom DNS](https://eero.com/support/articles/how-do-i-set-up-custom-dns-servers-with-eero)). eero Plus Advanced Security also reportedly does not cover guest-network devices ([Android Central](https://www.androidcentral.com/what-eero-secure-and-eero-secure)).

### Segmentation options, from free to thorough

NSA's home-network guidance calls for separate primary, guest and IoT wireless networks ([NSA, Feb 2023](https://www.nsa.gov/Press-Room/News-Highlights/Article/Article/3304674/nsa-releases-best-practices-for-securing-your-home-network/)). On eero there are three ways to get there. The cheapest is putting IoT on the guest network. It is free and reportedly isolates clients ([eero Community](https://community.eero.com/t/36605g/incorporating-eero-into-safer-network-for-internet-of-things)), but it breaks casting, HomeKit and Matter discovery and forfeits eero Plus protection. A second router for IoT in front of eero gives one-way isolation at the cost of double NAT. The thorough option puts eero in bridge mode behind OPNsense, pfSense or Firewalla. eero carries only the trusted LAN, and a VLAN-capable AP serves IoT and guest SSIDs on tagged switch ports ([Firewalla community](https://help.firewalla.com/hc/en-us/community/posts/26523457120275/comments/26526086243859); [OPNsense forum](https://forum.opnsense.org/index.php?topic=29886.0)). Firewalla itself recommends this layout with eero ([Firewalla bridge mode](https://help.firewalla.com/hc/en-us/articles/24044720058259-Firewalla-Bridge-Mode-Introduction-Newsletter-Feb-22-2023)). It is also the one option that restores per-device traffic visibility, which is why security and visibility goals converge on the same hardware decision. eero Profiles and device blocking are policy features, not isolation, and randomized MACs weaken them further.

### DNS filtering only holds if bypass is blocked

Pointing eero at Pi-hole, AdGuard Home, Quad9 or Cloudflare for Families gives network-wide filtering. Holding it requires defeating bypass. Answer NXDOMAIN for Firefox's canary `use-application-dns.net` ([Pi-hole issue #3167](https://github.com/pi-hole/pi-hole/issues/3167)). Block `mask.icloud.com` and `mask-h2.icloud.com` so Apple devices disable Private Relay ([Pi-hole discourse](https://discourse.pi-hole.net/t/icloud-private-relay/49811)). And block hard-coded resolvers and DoH IPs at the IP level ([jpgpi250 Pi-hole manual](https://jpgpi250.github.io/piholemanual/doc/Block%20DOH%20with%20pfsense.pdf)). That last step needs a real firewall. eero has no outbound rules, so a Chromecast that hard-codes 8.8.8.8 simply ignores Pi-hole. You must also set the IPv6 custom DNS fields, or clients resolve over IPv6 around the filter. A tool can *verify* enforcement automatically. It can resolve a known-blocked domain, attempt direct UDP/53 to 8.8.8.8 and TCP/853 to 1.1.1.1, and check the canary and Relay responses.

### Detection: new devices are easy, packets need a sensor

New-device alerting needs only the flat LAN. NetAlertX flags unseen MACs once you have marked the existing ones as known ([NetAlertX](https://github.com/jokob-sk/NetAlertX)), and eero's own device list provides a second, authoritative feed. Real IDS needs a traffic copy. Zeek's documentation accepts a SPAN port in SOHO settings ([Book of Zeek](https://docs.zeek.org/en/master/about/monitoring.html)). The working home design pairs Zeek's protocol metadata with Suricata's signatures on a two-NIC sensor, with NIC offloads disabled to avoid false positives ([nathanberg.io](https://nathanberg.io/posts/building-a-zeek-and-suricata-dual-sensor-for-a-home-lab/)). Wireless monitoring is separate again. Kismet with a monitor-mode USB adapter raises APSPOOF alerts for your SSID from a BSSID outside an allow-list, ADVCRYPTCHANGE alerts for a security-suite downgrade, deauth-flood alerts, and NOCLIENTMFP alerts for clients without management-frame protection. APSPOOF "will not detect attacks which also spoof the MAC address" ([Kismet alerts](https://www.kismetwireless.net/docs/readme/alerts/alerts/)). The allow-list is simply your eero BSSIDs, which a site survey already collects. That is a neat reuse of coverage data for security.

### The threat is your IoT devices being rented out

The dominant 2025–2026 threat is not someone breaking into eero. It is IoT devices conscripted into botnets that sell residential proxy bandwidth. Aisuru hit at least 700,000 devices and shifted from DDoS to proxy rental ([KrebsOnSecurity](https://krebsonsecurity.com/2025/10/aisuru-botnet-shifts-from-ddos-to-residential-proxies/)). Barracuda puts it at 1–4 million ([Barracuda](https://blog.barracuda.com/2026/04/13/top-threat-trends-of-the-2025-botnet-landscape)). The FBI warned in June 2025 that BADBOX 2.0 ships pre-infected on off-brand streaming boxes and projectors ([Infosecurity Magazine](https://www.infosecurity-magazine.com/news/fbi-smart-home-users-badbox-20/)). This shapes what a tool should check. It should flag uncertified Android TV boxes by vendor and model. It should watch per-device outbound bandwidth and destination diversity; eero's per-device usage and live burst data give a rough version of this without any sensor. It should check whether the public IP appears on abuse blocklists. Device exposure checks round this out: nmap `-sV` with the vulners script, Nuclei templates against HTTP admin panels, an external scan of your own public IPv4 and IPv6 hosts from a VM you control, and a Shodan lookup of your own IP ([ManageEngine](https://www.manageengine.com/network-configuration-manager/tech-topics/5-best-open-source-network-vulnerability-scanners.html); [VulnScanners](https://vulnscanners.com/blog/open-source-cve-scanner-guide)). NIST IR 8425A's router criteria make a reasonable scoring rubric ([NIST IR 8425A](https://nvlpubs.nist.gov/nistpubs/ir/2024/NIST.IR.8425A.pdf)). All active scanning must stay on networks you own, and passive Wi-Fi monitoring should log and alert only on your own BSSIDs and clients ([Tech Insider](https://tech-insider.org/how-to-run-a-vulnerability-scan-2026/)).

The unofficial API changes what an audit can automate. Some notes assumed eero settings were unreadable without the app. In fact UPnP, WPA3 mode, DNS mode, IPv6, guest network, port forwards, admin members and firmware status are all exposed through `settings`, `forwards`, `members` and `eeros` ([eero-api API Reference](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/API-Reference.md)). So an audit can read configuration directly rather than relying on the user to confirm it manually, and then cross-check it against observation. For example, it can compare the UPnP flag with an SSDP probe for an InternetGatewayDevice, and the WPA3 setting with the RSN suites in captured beacons.

## Fork the collector layer and build the missing join

### What already exists

The eero-cloud collector is a solved problem, so a new project should borrow it rather than rebuild it. **Dashboard_EERO** (MIT, pushed October 2026) is the most complete base. It provides traffic, per-device usage, signal history, speed tests with bufferbloat grades, a four-pillar health score, reservations and port-forward management, DNS sync to AdGuard, Pi-hole and Technitium, Prometheus, a 13-panel Grafana dashboard and MQTT with HA discovery. It is built on Python 3.12, FastAPI and async SQLite in WAL mode, with a self-hosted Alpine and Chart.js frontend and multi-arch Docker images ([Dashboard_EERO](https://github.com/EnricoFlammini/Dashboard_EERO)). **eeroVista** is deliberately read-only. It adds roaming detection, node-load reports, restart detection from uptime resets, and a retention template worth copying: raw data for 7 days, hourly aggregates for 30 days, daily aggregates for 365 days ([eeroVista](https://github.com/Yeraze/eeroVista)). The original schmittx HA integration (221 stars, last push September 2025) has been overtaken by the fulviofreitas fork, which needs HA 2026.8+ ([fulviofreitas/homeassistant-eero](https://github.com/fulviofreitas/homeassistant-eero)). A read-only **eero-mcp** server built on rusteero appeared in November 2026, but it has no track record ([eero-mcp](https://github.com/fulviofreitas/eero-mcp)). Adjacent tools fill other pieces: NetAlertX for discovery, Scanopy for auto-generated L2/L3 diagrams with Mermaid export ([Scanopy](https://github.com/scanopy/scanopy)), wifi-heatmapper for surveys and Kismet for wireless security. **No project merges eero node data with active discovery, spatial surveys and history to answer "why is room X slow."** That is the product.

### A reference architecture

The design that falls out of the research has four parts. The first is an **unprivileged core service** in Python and FastAPI. It hosts the eero poller (built on `eero-api`), SQLite with eeroVista-style rollups, the web UI, a `/metrics` endpoint, MQTT/HA discovery and an MCP server. Python wins because one language covers the eero SDK, scapy, zeroconf, pandas or DuckDB analytics and the MCP SDK. Go or Rust suit only the sensor agents. The second is a **privileged scanner container** with host networking and only `NET_RAW`/`NET_ADMIN`, running ARP, NDP, nmap and pcap jobs, mirroring NetAlertX's permission model ([NetAlertX](https://github.com/netalertx/NetAlertX)). mDNS and SSDP need no root and can live in the core. Do not `setcap` the Python interpreter, since that grants raw sockets to every script ([capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html)). The third is **sensor agents**: Linux probes in problem rooms, a laptop survey client or wifi-heatmapper import, and optionally a Kismet node. The fourth is an **optional security sensor** (Zeek and Suricata on a SPAN port) or a firewall in front of a bridged eero.

The central data model links several layers. Floor plans contain rooms. Rooms contain survey samples, each carrying x/y position, timestamp, BSSID, band, RSSI, PHY rate, iperf3 and latency. Samples join through BSSID to eero nodes. Nodes join through `source.location` to clients, and clients join through MAC to discovery enrichment (vendor, mDNS services, open ports, IPv6 addresses). Precomputed health scores and per-room summaries make ideal context for an LLM layer. The MCP surface should follow the pattern of samcsta/mcp-nmap. It refuses any scan unless a target allow-list is set ([samcsta/mcp-nmap](https://github.com/samcsta/mcp-nmap)). Read-only tools would run over stored data, a few bounded active diagnostics would be confined to the home subnet, and eero writes would be left out or gated behind explicit confirmation.

The tool's own security matters because **an eero token is a full-admin credential**. It can read the Wi-Fi password and the Thread network key and reboot the network. Use a dedicated invited admin account, never the owner or Amazon account. Store the token in a keyring or a 0600 file, as Dashboard_EERO does. Redact Thread keys and passwords from logs. Pin the token to the exact API host, as eero-api's transport does ([eero-api Authentication](https://github.com/fulviofreitas/eero-api/blob/HEAD/wiki/Authentication.md)). Bind the dashboard to the LAN and reach it remotely over Tailscale or WireGuard, not via a port forward.

For hardware, Raspberry Pi prices rose five times between October 2025 and October 2026 on DRAM costs. The Pi 5 2GB now costs $77.50 ([Phoronix](https://www.phoronix.com/news/Raspberry-Pi-5-2GB-Price-77.50); [Tom's Hardware](https://www.tomshardware.com/raspberry-pi/component-shortages-drive-raspberry-pi-prices-up-by-up-to-23-percent-escalating-lpddr4-lpddr5-costs-trigger-the-third-price-hike-of-the-year)), and reports of larger-model prices conflict. That makes an x86 N100 mini PC a strong candidate for the server role, though no sourced 2026 mini-PC price was found. Keep sensing separate from serving. Wi-Fi sensors need Linux with direct kernel control of the radio, which rules out VMs ([jantman](https://github.com/jantman/python-wifi-survey-heatmap)). morrownr/USB-WiFi is the reference for adapters with in-kernel MediaTek drivers ([USB-WiFi](https://github.com/morrownr/USB-WiFi)). An always-on Mac makes a poor headless sensor because of its Location Services gating.

### A phased roadmap

| Phase | Scope | Exit criterion |
|---|---|---|
| 0: Spike (2–3 weeks) | Run Dashboard_EERO or eeroVista plus NetAlertX in Docker Compose; dump raw `eeros` and `devices` JSON to confirm backhaul and topology fields | Know which fields exist on your hardware |
| 1: MVP | eero poller (60–120 s devices, hourly history), ARP/mDNS discovery merged by MAC, SQLite rollups, device/node pages, new-device and node-offline alerts via Apprise, `/metrics`, LAN-only binding; optionally an eero plugin for NetAlertX | Every device has an identity, a node and a signal history |
| 2: Coverage | Floor-plan upload with rooms; wifi-heatmapper JSON import or a Linux survey client; samples joined to eero nodes by BSSID; per-node and per-band GP heatmaps with uncertainty; one fixed probe in the worst room | Tool can explain the worst room using the diagnosis table |
| 3: Security audit | UPnP/forwards/WPA3/DNS read from API and cross-checked by observation; nmap/vulners and Nuclei on own hosts; DNS-bypass tests; external scan; scored report against NSA/NIST items | Repeatable weekly audit with diffs |
| 4: Intelligence | Read-only MCP server with scoped diagnostics; "why is X slow" reports; weekly digest | Natural-language answers grounded in stored data |
| 5: Optional depth | Android survey companion; Kismet WIDS with BSSID allow-list; Zeek/Suricata on a SPAN port or bridge-mode firewall | Wireless and traffic-level detection |

## Conclusion

eero is less of a closed box than it first looks. The binding limit is not API access, since the unofficial API is richer than most hobbyists expect, nor the rate limit. It is the physics of where measurements can be taken. eero sees every client from the access point. Only a probe in the room sees what the user experiences. Only a sensor on the wire sees traffic. The most valuable engineering in this project is therefore the joins: BSSID to node, node to client, client to MAC-keyed identity. Those joins turn three partial views into a diagnosis. They also produce the BSSID allow-list that wireless intrusion detection needs, so coverage work feeds directly into security work.

The decision with the largest downstream consequences is whether to keep eero in router mode. Router mode preserves Profiles, eero Plus and the full API device view, but caps security at DNS filtering you cannot enforce and a flat LAN. Bridge mode behind a firewall unlocks VLANs, DNS enforcement and per-device flows, at the cost of the eero features that made the system convenient. Build phases 0–3 in router mode, since they deliver most of the connectivity value and much of the security value. Treat the bridge-mode move as a deliberate later choice once the audit shows whether your IoT fleet warrants it. Throughout, design for the unofficial API to break someday. Keep the eero poller behind an adapter, store history locally, and make every feature degrade to scan-only mode.
